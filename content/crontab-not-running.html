Crontab Not Running: Debug It in 8 Steps

Your cron job isn't firing. Work through the 8 real causes: service down, wrong crontab, PATH, % escaping, permissions, logs — with commands.

Work top-down; the first four steps catch 90% of cases.

1. Is the cron daemon even running?

systemctl status cron (or crond). If dead: sudo systemctl start cron. This is embarrassingly common on containers and minimal installs.

2. Are you editing the right crontab?

crontab -l shows the current user's jobs. Editing /etc/crontab or dropping files in /etc/cron.d/ is a different world — those need a user field between the schedule and command.

3. Is the schedule what you think?

Five fields, minute first. Verify against the Cron Builder — the next-run preview catches field-order mistakes instantly.

4. The % escape

A bare % in the command becomes a newline; text after it goes to stdin. Escape as \%.

5. PATH is minimal

Cron runs with /usr/bin:/bin — your script calling python3, node or anything in a custom path fails silently. Use absolute paths, or set PATH= at the top of the crontab.

6. Where did the output go?

Cron emails stdout/stderr to the local mailbox: check /var/mail/$USER. Or log explicitly: append >> /tmp/myjob.log 2>&1 to the line — from now on you can see every failure.

7. Permissions and newline

Script not executable? chmod +x. Crontab file missing a trailing newline? Some cron implementations silently drop the last line.

8. Timezone and "it ran at the wrong time"

The job IS running — at server time. date on the server, then compare.

Steps 5–7 produce no errors anywhere — they just quietly don't work. Logging (step 6) turns invisible failures into visible ones; do it first, not last.
